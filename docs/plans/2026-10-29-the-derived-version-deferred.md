## What the branch built

`ENGINE_VERSION` had read the literal `"0.0.1"` for 391 commits, so the console header said `engine 0.0.1` and every `run_started` record in every log named a version that could not distinguish one engine from another. It is now derived from git at build and test time. `engine/scripts/write-version.mjs` writes `engine/version.json` — `<major>.<minor>` from `engine/package.json`, the patch from `git rev-list --count HEAD`, the build metadata from `git rev-parse --short HEAD`, and `.dirty` when `git status --porcelain --untracked-files=no` is non-empty — and npm's `prebuild` and `pretest` hooks in `engine/package.json` run it before every build and every test. `engine/src/version.ts` reads that file at module load through the new exported `readEngineVersion(file?)` and falls back to `UNBUILT_VERSION` (`0.0.0+unbuilt`) when it is missing or unparseable. The file is git-ignored (root `.gitignore:3-4`). Nothing else changed shape: `ENGINE_VERSION` keeps its name and its two readers, `engine/src/runner.ts:234`'s `run_started` payload and `console/server/app.ts:173`'s show answer, and `index.ts`'s `export * from "./version.js"` re-exports the two new names without an edit. The mechanism is visible in this branch's own numbers: the engine read `0.0.391+236d9b3` at the branch point, `0.0.392+8fce488` after Task 1's commit, and `0.0.393+835e051` after the fix round's.

## What is deferred, and what it costs

**The production rebuild must run `npm run build -w engine`, not only `npm run build -w console`.** `~/GitHub/Showrunner-prod` is a separate worktree with its own `node_modules` and `dist`, and `engine/version.json` is git-ignored, so it does not arrive with a `git pull` — it exists in that worktree only after the engine's `prebuild` hook has run there. The console reads the constant from the engine's build (`console/server/app.ts:7` imports `ENGINE_VERSION` from `@showrunner/engine`, which the workspace symlinks to `engine/`, whose `main` is `./dist/index.js`), so a rebuild that skips the engine leaves the production console reading whatever `engine/version.json` was last written there — nothing at all on the first rebuild after this merge. Note also that **`npm ci` and `npm install` do not write the file**: there is no `prepare` hook, only `prebuild` and `pretest`. Cost if the engine is skipped: the header reads `engine 0.0.0+unbuilt` and every run log written by that console records `0.0.0+unbuilt`, which is a worse answer than `0.0.1` was, because it looks like a defect rather than a stale constant. The recommended production sequence is `git pull && npm ci && npm run build` at the repository root, whose `build` script already runs engine, tools and console in that order.

**A copy of `dist/` without `version.json` beside it reports `0.0.0+unbuilt`, and nothing stops that copy being made.** `readEngineVersion` resolves the file one level above its own module, which is `engine/version.json` from both `src/version.ts` and `dist/version.js`; a `dist/` tree moved, tarred or rsynced on its own loses the file, because it sits beside `dist/` and not inside it. `engine/package.json` has no `files` field today, so no packaging list was updated and none would carry it. Cost: a deployment assembled by copying `engine/dist` reports `0.0.0+unbuilt` in the header and in every run log, silently and forever, with no error anywhere. The string is deliberately recognizable so the case is visible when someone looks; nothing makes anyone look.

**The console and tools packages keep their own static `"version": "0.0.1"`, and only the engine's number is derived.** `console/package.json:3` and `tools/package.json:3` are untouched by this branch, and nothing reads them for display. Cost: "the version" is now two different kinds of thing in one repository — a derived string for the engine and a hand-written placeholder for the other two — and a reader who sees `@showrunner/console@0.0.1` in npm's script banner may reasonably conclude the derivation did not take. The engine is the package whose identity matters in a log, which is why it is the one that was done; extending the writer to the other two is a half-hour of work nobody has asked for.

**`engine/package.json`'s own `version` field also stays `"0.0.1"`, by design.** The writer reads only its major and minor, so the field is now the place a deliberate `0.1.x` or `1.0.x` bump is made and nothing else, and npm's own banner keeps printing `@showrunner/engine@0.0.1` above every script this repository runs. Cost: the banner and the engine's real version disagree on every build, and the disagreement is permanent rather than a bug to be fixed. Anything reading `ENGINE_VERSION` — the header, the run log — sees the derived string; only npm's banner shows the field.

**The non-git path is reasoned about and not tested.** `engine/test/version.test.ts` runs the writer inside this checkout, where git always succeeds, so the `catch` that produces `<major>.<minor>.0+unknown` has never executed in a test. Exercising it needs a temporary directory that is not a git worktree plus a copy of the package manifest, or a `PATH` with no git on it. Cost: the tarball fallback could be broken — a thrown `ReferenceError` in the catch, say — and every gate would stay green. The blast radius is small, because the only consumers of that path are builds outside a checkout, which this project does not currently make.

**Three `"0.0.1"` literals remain in `console/test` and were deliberately left.** `console/test/what-happened.test.ts:23`, `console/test/runs.test.ts:60` and `console/test/runs.test.ts:94` build synthetic `run_started` payloads that carry `engineVersion: "0.0.1"`, which the console parses back at `console/server/runs.ts:379-383`. These are log *data*, not assertions about the engine's constant — a log written by the engine before this branch genuinely does say `0.0.1`, and the console must keep reading it. Cost: a future reader greps `0.0.1`, finds three hits in the console's tests, and believes the old constant is still pinned somewhere. This paragraph is the answer to that grep.

## Not built

No CI check asserts that the version advanced, because there is no CI; the guarantee is structural — the patch is a property of the commit graph, so it cannot fail to advance — rather than enforced. No tag, release or changelog is derived from the number: `0.0.393+835e051` appears in the console header and in run logs and nowhere else. No `git describe` and no tag-relative count: the patch is the absolute count from the root commit, which is monotonic along any ancestry and identical for a merge taken in either order, but **not globally unique** — two unmerged tips the same distance from the root share a patch number, which is what the `+<shorthash>` metadata exists to disambiguate. Nothing writes the version into `engine/package.json`, so `npm version` and the field itself stay a human's business.
