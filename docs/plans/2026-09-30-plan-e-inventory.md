## 1 · Console v1 measured

**Console v1 is a read-and-act layer over the Archon CLI and the show's files, and roughly one third of it is dead the moment Archon is.** Of the 33 routes, **13 exist only to read or drive Archon's run state** (`/api/runs`, `/api/run/:id`, `/api/run/:id/gate-diff`, `/api/engine`, `/api/actions/launch`, `/api/actions/gate`, `/api/actions/gpu-busy`, and the SSE feed's poll half) or to shell a Python script the engine now owns (`/api/board`, `/api/actions/reroll`, `/api/actions/ambient-pass`, `/api/actions/casting-pile`). **Ten more serve surfaces spec §7.2 defers** (the season map, the desk, discuss, notes). What survives without rewriting is the artifact-serving layer: the four `/media` routes, the episode-document route, and the scene/shot join.

### 1.5 How v1 launched and detached runs, and how it showed progress

**Console v1 does not obey the ops law it was measured against.** Process map §7 (`docs/specs/2026-09-25-pipeline-process-map.md:440`) states the law: "launch, approve, and reject must be run **detached** — `( nohup archon workflow <verb> <args> > "$LOG" 2>&1 < /dev/null & )` — because a console approve was not reliably safe and cost half a day." The measurement of v1 against that law:

| Action | argv v1 composes | Detachment | Verdict against the law |
|---|---|---|---|
| Launch | `["archon", "workflow", "run", <workflow>, <message>, "--detach"]` (`actions.ts:103`) | Archon's own `--detach` flag; the `spawn` itself sets no `detached` option (`actions.ts:215-218`) | **Partly.** The Archon run detaches from the console; the CLI process that starts it does not |
| Approve | `["archon", "workflow", "approve", <runId>, <text>]` (`actions.ts:135`) | **none** — no `--detach`, no `nohup`, `detached` not set | **No.** The approve runs as a direct child of the Hono server, its combined stdout and stderr streamed to the browser through `streamActionResult` (`console/server/index.ts:353-372`). This is the shape that cost 5½ hours on ep10 |
| Reject | `["archon", "workflow", "reject", <runId>, <text>]` (`actions.ts:135`) | **none** | **No**, identically |
| Re-roll / ambient / casting pile | `uv run <script>` argv arrays (`actions.ts:58`, `:71`, `:92`) | **none** | **No** — a long GPU pass dies with the server |

`actions.ts:198-231` `runStreaming` is the single spawn path for all six action routes: `spawn(argv[0], argv.slice(1), {cwd, env})` with no `detached`, both pipes drained into one `onChunk` callback, resolving `{code}` on `close` with a `null` code normalized to `1` (`:229`). **The engine closes this by construction**: spec §4.2 (`docs/specs/2026-09-25-console-rewrite-design.md:116`) — "Detached execution stops being an operator discipline and becomes the only path, because runs are server-side jobs rather than CLI processes someone must remember to `nohup`" — and spec §6.9 (`:184`) — "Detachment is therefore structural: there is no terminal process to detach from." See F-01 and F-02: the engine moves the problem rather than dissolving it, because the server is the process the run now lives inside.

**How v1 showed progress, and what it could not show.** v1 had no per-step progress at all. Its three signals:

1. **A derived node rail.** `archon.ts:251-287` `buildRail` infers each node's state from whatever Archon supplies, in five tiers of specificity: a node id named inside `metadata.error` in single quotes (`:259-263`); `current_step_name` (`:265`); `metadata.approval.nodeId` (`:269`); `metadata.node_counts.completed` as a positional approximation (`:275`); an honest all-`pending` rail (`:286`). Node ids come from regex-scanning `.archon/workflows/<name>.yaml` for `^ {2}- id:\s*(\S+)` (`archon.ts:197`, `:204-215`). **`archon.ts:11-38` records why**: neither `runs --json` nor `get --json` returns a per-node array, and `current_step_index`/`current_step_name`/`total_steps`/`current_step_status` "were null on every sampled run (12 completed, 4 failed, 5 cancelled)."
2. **Whole-run elapsed.** `components/Rail.tsx:38-73` `elapsedRunLabel` from `started_at`, which `archon.ts:50-56` notes is the only real timing the CLI carries — used for the current node's "elapsed" too, "for lack of any per-node alternative."
3. **The browser tab title.** `src/useDocTitle.ts:46-60` `titleFor`: a paused run wins over a running one and yields `⏸ <ep> NEEDS YOU — Dead Light`; an active run yields `● <ep> <stage> · <N>m — Dead Light`. `:36-45` records that this string plus the amber banner are "the entire alerting story" because LAN HTTP is not a secure context and iPad Safari will not grant web notifications.

**That is exactly the gap spec §6 was written to close.** Spec §6 (`docs/specs/2026-09-25-console-rewrite-design.md:150`): "Archon could name the stage it was in and never the position inside it, and the ep09 and ep10 failures (a loop returning in three seconds per iteration having done nothing) were invisible until a human read a partial script."

**The live feed's shape.** `console/server/sse.ts:143-243` `startLiveFeed` runs two publishers onto one bus (`sse.ts:24-57`): a self-rescheduling Archon poll at 3 s while any run is non-terminal and 15 s otherwise (`:70-71`, `:186`), publishing only on a changed `JSON.stringify(result)` (`:180-183`); and a `chokidar` v4 watch of `Episodes/` and `Production/` recursively, debounced 500 ms per path (`:72`, `:219-230`), filtered by four regexes because chokidar v4 dropped glob support (`:84-91`). The client subscribes with a native `EventSource` and an explicit 2 s reconnect (`src/api.ts:186-235`), and the vocabulary is exactly two event types, `runs` and `fs` (`api.ts:186`). **Every page's reaction to either event is `refetch()`** — `pages/Episode.tsx:176-177`, `pages/Scene.tsx:314`, `pages/GateRoom.tsx:503-505`. See F-03.

### 2.2 The gaps a server exposes

Each gap below is measured against the engine as `plan-e` was cut, not inferred.

**2.2.1 `run()` is one in-process call that returns at a gate or at the end, and nothing in the engine calls it again after `answerGate`.** `runner.ts:161` returns `{status:"waiting", gate}` the moment `deriveRunState` reports an open gate, and `runner.ts:226` returns the same when a gate opens mid-pass. `answerGate` (`:34-53`) appends one event and returns `void` — it starts nothing. **The engine has no loop, no scheduler, and no caller.** Every existing caller is a test: `engine/test/gate.test.ts` and `engine/test/e2e.test.ts` call `run`, `answerGate`, `run` again by hand. A run of the episode pipeline crosses **eight** gates (`episode.ts:35-38`), so **one episode is at least nine `run()` calls**, and the ninth returns `{status:"completed"}`. Whoever owns the loop owns the job queue. See F-01.

**2.2.2 The `active` map is per-process, and the resume contract says so.** `runner.ts:129`: "The runs in flight, keyed by the resolved path of the log each one is writing." `runner.ts:132-139` sets and deletes the entry around the awaited promise. A second OS process holding the same show repository — a second `npm run dev`, a CLI invocation, a second show server pointed at the same path, or the same path reached through a symlink — sees an empty map and duplicates every step. This is O-01 and O-17. See F-02.

**2.2.3 A rejected `run()` promise is a real outcome, not a bug, and the server must catch it.** `engine/src/steps.ts:185-189` states the rule: "An executor may throw only when the event log itself is unwritable. The script executor never throws…; the agent executor guards the `agent_tool_call` emit the same way but its `agent_query` and `agent_result` emits are unguarded and reject out of the executor. A throw leaves the step `running` with no terminal event; §6.9's replay re-executes it on the next run." The unguarded emits are `agent-step.ts:266` (`agent_query`) and `:344` (`agent_result`); the guarded one is `:289`, wrapped at `:290-292` into `EmitFailure`. A guard's throw **is** caught and converted (`runner.ts:282-290`), so the asymmetry is agent-step-only. This is O-13. See F-09.

**2.2.4 `killLiveProcessGroups()` rethrows a non-`ESRCH` error mid-iteration, and the SDK's children are not in the registry at all.** `script-step.ts:40-51`: the loop over `live` catches `ESRCH` and rethrows everything else at `:47`, so an `EPERM` on the third of five groups leaves two un-signalled and the count unreturned. The registry holds only script children: `live.add(child.pid)` at `script-step.ts:61` is the only writer. The agent executor's one lever is `abortController.abort()` (`agent-step.ts:244`, aborted in `pump` at `:134`), and the SDK's child process pid is never recorded — `sdk-query.ts:19-39` copies eight fields off each message and no pid. These are O-02 and O-12. See F-10.

**2.2.5 `EventLog` has no tail and no watch; `read()` is the whole file, every time.** `events.ts:39-59`: `readFile(this.path, "utf8")`, split on newline, `JSON.parse` per line, returning a fresh array. There is no offset parameter, no stream, and no `fs.watch`. `runner.ts:153` reads the log **exactly once per run** and then keeps the array in memory, appending to both file and array through one closure (`:154`) — `runner.ts:150-152` states this explicitly. **So the runner never re-reads, and any reader outside the run process must poll the whole file.**

**2.2.7 `answerGate` is attempt-blind.** `runner.ts:44-52` reads the log, checks the run id and that the gate is open, then writes the answer stamped with **the log's** current `attempt` (`:49`), never the attempt the caller was looking at. **2.2.8 `deriveStage` takes one run's state, and an episode has several runs.** `stages.ts:62` signature is `deriveStage(state: RunState, map, needs)` — one `RunState`, from one log. See F-12.

**2.2.10 `resetSteps` on a run with an open gate leaves the gate open, and the resets take effect only once the gate is answered.** `runner.ts:84-85` appends `run_resumed` (only if finished) and one `step_reset` per id; `state.ts:53-62` deletes the step's status and result. This is O-21's first half.

**2.2.11 A failed run still reports its highest approved stage.** `stages.ts:70-73` walks `state.steps` for completed steps mapped in `map.approved`, and `stages.ts:63` returns `map.final` only for a completed run — a failed run falls through to `highest`, which is whatever the last approved milestone was. So an episode whose `render` failed after four hours shows **`AUDIO`** or **`IMAGES`** on the board with no sign of the failure. This is O-07. See F-04.

**2.2.12 `step_cached` carries no reason, and three of the four terminal events omit the step `kind`.** `runner.ts:321` emits `step_cached` with `{inputHashes, outputHashes, result?}` — no reason string. `step_started` carries `kind` (`runner.ts:278`, `:328`, `:341`, `:492`), but `step_completed` (`:292`, `:335`, `:349`), `step_failed` (`:288`, `:331`, `:344`) and `step_skipped` (`:207`, `:215`) do not. A run view that colours a row by step kind must join each terminal event back to its `step_started`. This is O-05.

**2.2.13 A crashed loop iteration and a no-op loop iteration are both `toolCalls: 0`.** `runner.ts:507` emits `{iteration, max, sentinel: false, toolCalls: r.toolCalls ?? 0, error: r.error}` on a failed iteration; `:512` emits `{iteration, max, sentinel, toolCalls}` on a successful one. The distinction spec §6.7 asks the dashboard to surface in real time — "an iteration with zero tool calls is flagged on the dashboard the moment it happens" (`docs/specs/2026-09-25-console-rewrite-design.md:180`) — is available only by reading `error` alongside `toolCalls`. This is O-06.

**2.2.14 `ctx.events` is the live array.** `runner.ts:154` pushes every appended event onto the same array handed to `RunContext.events` (`:170`), so a guard that keeps the reference observes later events. `engine/src/steps.ts:27-31` documents the field as "the run's log as read so far" and notes "executors ignore it." This is O-24; it bears on any console-side guard Plan E adds.

**2.2.15 The agent executor's session map is per-executor and unbounded.** `agent-step.ts:191` creates one `Map<string, string>` per `createAgentExecutor` call, keyed `${episodeId}/${runId}/${stepId}` (`:248`), written at `:315`, never evicted. `agent-step.ts:185-190` explains why the episode id is in the key: "one long-lived executor (a console process that runs several episodes in turn) would then resume the first episode's session inside the second." **A server that builds one executor at startup is exactly that process.** This is O-15.

**2.2.16 The agent executor's message handler is not raced against the deadline.** `agent-step.ts:124-126`: "onMessage is not raced against the clocks: a stalled handler — a log append that blocks — delays the deadline by its own duration, and the clock is observed at the next `next()`." Plan E owns the log writer. This is O-14.

**2.2.17 Cost is an estimate.** `agent-step.ts:349` records `costUsd` from `total_cost_usd`, which `sdk-query.ts:29` copies off the SDK result. O-16 (`docs/plans/2026-09-27-agent-runner-deferred.md:42`) states it is the SDK's client-side estimate, not billing data.

**2.2.18 Two message-text defects, both cosmetic and both Plan E's.** `answerGate` on an empty or absent log throws `run id mismatch` (because `deriveRunState` returns `runId: ""` for an empty array, `state.ts:28`, and the check at `runner.ts:45` fires first) rather than `gate "<id>" is not open` — O-04. `formatAired` passes a bare ordinal to `InvalidEpisodeId`, whose constructor labels it the raw id (`ids.ts:2-4`, called at `:45-46`) — O-08.

**2.2.19 `EventLog.logPath` hardcodes `Production`.** `events.ts:27` joins `showRoot, "Production", episodeId, "runs"`, while the pipeline derives every other path from `show.productionDir` (`episode.ts:62`, `:66`). **What the spec's wording requires that the data does not supply.**

2. **An episode's title.** v1 got it from `Canon/season-N.md`'s quoted cell (`console/server/repo.ts:45`, `:60`) or from the first quoted string in `script.md` (`repo.ts:92-99`). The engine reads no season document and `showrunner.json` carries no titles. See F-08.
3. **An episode with no run at all has no `RunState` to derive from.** `deriveRunState([])` returns `{runId: "", finished: false, steps: {}, results: {}, gateAttempts: {}}` (`state.ts:28`), and `deriveStage` on that returns its floor, **`IDEA`** (`stages.ts:69`) — unless `ideaMissing` is true, in which case the `NEEDS_IDEA` rule fires (`:57`, `:77-78`). So an episode directory with a written `premise.md` and no run reads as `IDEA`, which is correct, and one without reads as `NEEDS_IDEA`, which is also correct. **But `episodeNeeds` needs the episode id to exist as a directory first.** See F-15.
4. **A failed run's stage hides the failure** (§2.2.11, O-07). The Board must show run status beside the stage.
5. **A `NEEDS_` state and an open gate coincide, and `deriveStage` returns only one string.** `stages.ts:76-79` checks the `NEEDS_` rules **before** the open-gate branch at `:81`, so `NEEDS_IMAGES` wins over an open `nano-banana-gate`. This is O-23; the record says "the board should say both." The Board therefore needs `state.openGate` alongside the stage, not only the stage. See F-16.

**How the console would hand the assembled context to an agent, measured against what exists.** Two mechanisms are present in the two repositories:

- **`sdkQuery` through `createAgentExecutor`** (`engine/src/agent-step.ts:184`, `engine/src/sdk-query.ts:7`). The executor's signature is `(step: AgentStep, ctx: RunContext, emit: Emit) => Promise<AgentOutcome>` (`engine/src/steps.ts:202`), so using it for a troubleshooting query means **inventing an `AgentStep` and a `RunContext` for something that is not a pipeline step**, and every `agent_query`/`agent_tool_call`/`agent_result` it emits goes through `emit`, which stamps a step id into a run's log (`runner.ts:149-153`). A troubleshooting query would write itself into the log it is reading. Calling `sdkQuery` directly avoids that — it is exported from the barrel (`engine/src/index.ts:13`) and takes `{prompt, options: AgentQueryOptions}` (`agent-step.ts:45`) — but then nothing logs the query at all.
- **`claude -p`, as console v1's *discuss* did.** `console/server/discuss.ts:493-497` `runClaude(prompt, cwd, spawnFn)` spawns `claude -p <prompt> --allowedTools Read` as an argv array with a 300 s budget (`:425`) and classifies five distinct failure shapes (`:462-492`), keeping a severed reply on `partial` rather than discarding it. Spec §4.5 (`docs/specs/2026-09-25-console-rewrite-design.md:122`) notes that "the console's *discuss* feature already shells `claude -p`" as the evidence that the Agent SDK is the least-change replacement.

Spec §6.8 does not say which, and neither does §4.5. See F-20.
