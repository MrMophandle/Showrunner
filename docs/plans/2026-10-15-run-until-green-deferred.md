## What Plan J established that later plans build on

- **A `panel` step kind re-runs a set of earlier steps on a verdict, which only a gate rejection could do before.** `PanelStep` is `{ kind: "panel"; id; dependsOn; reviewers: StepId[]; resets: StepId[] }` (`engine/src/steps.ts`), and `runPanelStep` (`engine/src/runner.ts`) returns the `{ kind: "reset", stepIds }` arm that `runGateStep` used to be the only producer of (inventory J-02). `orderSteps` refuses four things at load time: a panel with no reviewer (every round would be green by vacuity), an unknown id in `reviewers`, an unknown id in `resets`, and **a reviewer the panel does not depend on** — the last because the ordered walk is the only thing that guarantees a verdict exists when the panel is reached.
- **The round's number comes from the log and nothing else, and the guard that makes it idempotent has two clauses.** Round N is one more than the number of `panel_round` events this step has written, counted over the **whole run** — `run_resumed` does not reset it, so the operator's Resume continues the loop at the next round instead of restarting at round 1. The guard is (a) a `step_reset` signed `panel:<id>:round-<N−1>` exists after this step's last `step_started`, **and** (b) at least one id in that batch has not been visited since it (a `step_completed`, a `step_cached` or a `step_skipped` all count as a visit). Clause (a) alone fires on every ordinary red round and would pay for a second panel; clause (b) is what distinguishes "the crashed run still owes the re-runs" from "the re-runs happened, judge them".
- **A recovered partial batch re-runs the stale steps only** (`58c56b2`). The recovery branch returns `stepIds: stale` rather than the whole declared set, because the runner drops the result of every id the outcome names: naming a step that had already re-run in the same pass would delete a fresh completion and run it again — a second writer call inside one round, against the one-fresh-`revise`-per-round invariant.
- **`panel_round` is the record of a round, and it is wider than a board of verdicts.** The twentieth `EventKind` (`engine/src/steps.ts`), payload `{ round, green: false, verdicts, costUsd, weeklyUtilization?, by }`, written immediately before the reset batch. `verdicts` is keyed on **every** id the round resets whose result the run had: the seven panel verdicts, the hand-edit guard's JSON record, the canon ledger's result line, and from round 2 the writer's own round report. It changes no status — `deriveRunState` has an explicit `case "panel_round": break;` with its reason — because the reset beside it is what moves the steps.
- **The weekly quota is the only stop, and it is a step failure rather than a sleep.** A red round whose latest `agent_result.usage.sevenDay.utilization` **after the last `run_resumed`** is at or above `agents.autoRetryWeeklyUtilizationMax` (default 65) writes only `step_failed`, with `panelStopSentence` (`engine/src/agent-step.ts`), which shares its opening, its bare percentages and its parenthesised config key with Plan I's sentences: `Manual resume needed: the panel is still red after round 3 and the weekly quota is at 78%, at or above the 65% auto-retry ceiling (agents.autoRetryWeeklyUtilizationMax); press Resume after the reset to continue the loop.` No round and no reset are written, so the Resume comes back to the same round. An **unknown** figure is never a stop.
- **Two new prompt variables, one of which renders a word where every other hole is an error.** `{{prior.<stepId>}}` is that step's verdict in the previous round, read out of the latest `panel_round` rather than out of `ctx.results`, which the round's own reset emptied (inventory J-14); a step with no previous verdict renders the literal `none`. `{{round.n}}` and `{{round.costUsd}}` come from the same records through the exported `roundExtras(events)` — a red `panel_round` means the round about to run, a green `step_completed` means the round that passed — and the console reads the same function through `roundOf`, so the gate's message and the gate's head cannot disagree.
- **The usage call is asked on every query, because it is the only source of the weekly figure.** `sdk-query.ts`'s generator body became the exported `streamWithUsage(q, drop)`, which asks the SDK's experimental usage call once per query at the first message, mid-stream, and yields one synthetic `usage` message; `agent_result` carries it as `usage` when the wrapper yielded one. The probe quoted below is why this is the mechanism and not a belt-and-braces extra.
- **`revise` is one fresh writer call per round, with no sentinel.** It is an agent step with the same id as the retired loop, `context: "fresh"`, `dependsOn: ["hand-edits-script"]`, and a `when` that asks whether the log holds a `panel_round` — so it is bypassed on round 1 and runs once per round after that. It is **declared before the reviewers** and the seven reviewers depend on it, which is load-bearing at the console's production `--concurrency 7`: without the edge the writer and the panel land in one batch and the reviewers read the script while it is being rewritten.
- **The reviewers have one form, and it is mechanical where it used to be a judgment.** Each of the six checks now states "`pass` is true only when `issues` is empty", cites each issue as `<law file>:<section or line>` plus the script line, carries a non-failing `notes` list, accounts for every prior issue by id in `prior: { resolved, unresolved }`, and reads its own previous verdict under a `## Your prior verdict` heading. Issues are objects with stable ids (`{ id, law, line, text }`) so the next round can name the same finding. `revise.md` states the precedence (canon outranks; a law-and-line citation outranks judgment; a one-line conflict is resolved by the cited law and recorded), reads all seven verdicts as `{{prior.<id>}}`, and must end with `## Changed` and `## Deliberate exceptions` — the two headings the next round's reviewers read, which makes them a machine-read convention like the outline's `## Cast` section.
- **The console says which round a run is on and what it has cost**, from `roundOf(events)` wrapping the engine's `roundExtras`: `RunView.round`, `EpisodeRow.round` and `GateView.round`; the working sentence appends `(round N)` from round 2 on; the gate head prints `· round N · $X.XXXX ·` including a green round 1; the feed summarises `panel_round` as `round 2 red — tone-check, repetition-check · $6.0660`.

## Not built

- **No round cap of any kind.** Ryan's ruling: the weekly quota is the only stop. So a prompt regression that makes one reviewer unable to pass spends $6.07 of panel plus $3.23 of revision per round until the account-wide seven-day figure reaches the ceiling, and an executor that emits no `usage` at all — every fake-executor test, every log written before `8ea41d9` — never stops. Task 2's mechanical pass rule is what bounds it, and it is a prompt rather than a mechanism.
- **A verdict summary in the template language.** `renderValue` pretty-prints any object and the template language cannot express a summary (J-16), so the gate's message carries two numbers and the per-reviewer detail stays on the gate page. Nothing in the engine shortens a verdict.
- **A second weekly source.** The stream's seven-day `rate_limit_event` is still read first when one arrives with a utilization on it, and the probe says it does not arrive. The order is, on current evidence, decorative.
- **Any warning before a quota is reached.** `rate_limit_info.status` carries `allowed_warning` and nothing reads it (Plan I's record); a round learns the week's figure from the last `agent_result` and nothing anticipates it.
- **A per-round or per-run cost ceiling.** `{{round.costUsd}}` is reported to the showrunner and to the console and is compared against nothing: no step fails on cost, and `maxBudgetUsd` remains a per-query bound on the SDK side.
- **The instance's prompts, and anything on the operator's screen.** Task 5 is the show side; and with no console build on this branch the Board, the Run view, the gate head and the feed keep their pre-Plan-J behaviour until the controller rebuilds and restarts the 4410 server from the merged `main`.
- **A live multi-round exercise.** `engine/test/run-until-green-exercise.test.ts` walks the real pipeline with a scripted SDK seam, and `engine/test/ep98-exercise.test.ts` walks the real scripts with no agent at all. Nothing walks real agents through two rounds; the first one will be a production run of an episode's write phase after Task 5 merges.
