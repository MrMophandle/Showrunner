## What Plan I established that later plans build on

- **The SDK's limit signals reach the engine.** `engine/src/sdk-query.ts`'s `toAgentMessage` copies an assistant message's `error` kind verbatim (one of the thirteen `SDKAssistantMessageError` kinds) beside that message's text blocks, and maps a `rate_limit_event`'s `status`, its `rateLimitType` → `window`, its `utilization`, and its `resetsAt` from **epoch seconds** to an ISO string through a `resetsAtIso` helper that drops a non-finite value rather than throwing. `sdkQuery` holds the query object and, after the first mapped message whose `rateLimit.status === "rejected"`, yields one synthetic `{ type: "usage" }` message from the exported `usageMessage(q)`. That call is the SDK's `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET()`, so it is wrapped three ways: a missing method, a throw, and no answer inside ten seconds all answer `{ available: false }`, and none of them can fail a query.
- **A limited query is classified, and the classification has a precedence.** `classifyLimit` in `engine/src/agent-step.ts` puts a deadline, a rejected `emit` or a handler fault **above** any limit (a timeout that coincides with a limit is still `timeout after <n>ms`), and puts a limit **above** the result message's subtype — which is the whole point, because the measured limit arrived as `ok: true, subtype: "success"`. The assistant `error` kind is read first and a rejected `rate_limit_event` with no error kind beside it still classifies.
- **The executor keeps the last *rejected* event apart from the last event** (the fix round, `e92df80`). One stream reports several windows, so a five-hour rejection followed by an `allowed` seven-day event would otherwise read as a seven-day limit and the step would refuse to wait out the window it could have waited out. `limitedWindow` and `limitedReset` read `a.rejected ?? a.rateLimit`, so a limit arriving as an assistant `error` with no rejection beside it still names a window.
- **The weekly figure has two sources, in a fixed order:** the stream's own seven-day `rate_limit_event` first (`weeklySource: "event"`), the experimental usage call as the fallback (`weeklySource: "usage"`). A seven-day event with no `utilization`, or a non-finite one, is not a figure and leaves the question to the call. **A weekly *limit* and the weekly *figure* are two different tests, and the fix wave separated them.** For classification, a seven-day kind is any window whose name begins `seven_day` (`isSevenDay`), which covers all four the SDK declares — all four are limits the engine never waits out, and all four read "7-day" in the operator's sentence. For the figure, only the **account-wide** `seven_day` window counts (`isAccountWeeklyWindow`): a `seven_day_opus` event at 90% would otherwise block a wait the account-wide window at 20% allows, and a `seven_day_sonnet` event at 5% would authorize a wait the account-wide window at 95% forbids. That is the same choice `toUsage` already made about the usage call's per-model rows, so the two sources now answer one question. `agent_result.limit.weeklySource` records which source answered, and is absent exactly when `weeklyUtilization` is.
- **Ryan's rule of 2026-10-15 is applied in the agent executor, before any of `runner.ts`'s three callers sees the outcome.** A `five_hour` window **and** a numeric seven-day utilization **strictly below** the ceiling **and** a known reset time **and** no wait taken yet → the step logs `step_waiting`, sleeps until **one minute past** the reset, and re-runs the same query resuming the same session, **exactly once**. Everything else fails with one sentence naming the window, the reset, the weekly figure and the operator's move. The clock and the sleeper are injectable (`AgentExecutorOptions.now` and `.sleepUntil`) for the tests only; production passes neither.
- **The ceiling is a show-config key:** `agents.autoRetryWeeklyUtilizationMax`, default 65 through the exported `DEFAULT_AUTO_RETRY_WEEKLY_UTILIZATION_MAX`, an integer 0–100 refused at load by its dotted name, `requiredBy: "none"`. `SHOW_CONFIG_KEYS` now holds **sixty-one rows — eight `both`, forty-three `scripts`, ten `none`** (measured from the array at `1962780`, and the census in the `ShowConfigKey` doc comment agrees). `tools/src/init/config.ts` writes the group into every new show's `showrunner.json`, so the dial is visible to an author who never reads the README.
- **The wait is an event, and the step stays in flight.** `step_waiting` is **one of nineteen** `EventKind`s and the newest of them (`engine/src/steps.ts:6-13`), the agent executor's to write and nothing else's (`engine/src/agent-step.ts:734` is the only emitter), with the payload `{ reason, window, resetsAt, ceiling, weeklyUtilization? }`. `deriveRunState` gained an explicit `case "step_waiting"` (`engine/src/state.ts:66`) that marks the step `running` and **touches nothing else** — in particular not `position` (ruling I-21). So a wait neither ends a step nor moves the Run view's altitude to it, a log whose `step_started` was lost to a crash still reports the step `running`, and the step's elapsed time is read off the console's own `StepRow.startedAt`, which `projectSteps` holds at the `step_started` value through a wait: "how long has this step been going" counts the wait rather than restarting at it.
- **The console draws the wait from that event and nothing else** (design §4.2: the server owns no run state). `StepRow` gained `note` (the reason, verbatim) and `waitingUntil` (the reset ISO); `projectSteps` sets both on `step_waiting` and **clears both** on the retry's `agent_query` and on `step_completed`, `step_cached`, `step_failed`, `step_started` and `step_reset`. The `agent_query` case is the fix wave's (the whole-branch review's one behavioural finding): the sleep ends when the executor queries again, and the query that follows a wait ran 447 s in the measured case, so a note left standing until the step's terminal event had every surface asserting a sleep through minutes of work — with a reset time already in the past in the tab title. It is guarded on the note's presence, because the first attempt's `agent_query` precedes `step_waiting` and because a gate's fix agent writes one against a `waiting` row that carries no note. `EpisodeRow` gained `waitingNote` and `waitingUntil` through a private `waitingOf(steps)`, the twin of `failedOf`. The Board prints the sentence under the stage chip; the Run view prints it as a third line in the step altitude; `StepRail` prints it per row (an addition beyond Task 2's brief, and the load-bearing one: a worker runs up to seven agent steps at once, so the limited step is usually not the one the altitudes draw); `EventFeed` summarises the kind as its reason; `Bible.tsx`'s running panel carries it for a setup run. The tab title gained `⏳ <id> WAITING · resets <time> — <show> · <key>`, **third of five forms**, keyed on the note's presence rather than on a status — a sleeping worker's run reads `running` because its lock is still beating.
- **A waiting step keeps its progress bar and its loop flag.** `projectSteps` computed both only for `status === "running"`; the guard is now `if (row.status !== "running" && row.note === undefined) continue;`, which includes a limit wait and still excludes a gate's. The measured failure (the plan's "What was measured") is a revise loop limited on iteration 1 of 3, so the bar and the zero-tool-call flag are exactly what an operator wants kept through the wait, and both halves of that guard are now pinned (the fix wave added the zero-tool-call iteration the first test's seed lacked). **A waiting row also keeps its "since the last event" clock out of amber** (`quietRow` on the Board, `stallState`'s waiting branch on the Run page): the age is still printed, because five hours of silence is the number the operator wants, but the colour that means "this may be stuck" is withheld for the one silence the console asked for.
- **The gate's `waiting` and a limit's `waiting` did not need telling apart, and Task 2 proved it by reading all seven call sites** rather than inferring it: every gate move keys on the **run's** `openGate` or the run's status, never on a step row's status (measured at this record's commit: `ActionBar.tsx:49-53` and `:77`, `Board.tsx:229`, `projections.ts:287`, `server/runs.ts:296`). No seventh step status was added.

## The one live measurement, and what it settles

**A real plan usage limit cannot be provoked in a test**, so Plan I's proof is the fake stream plus one live probe.

**The fake stream** is the `fake(messages, opts)` seam at `engine/test/agent-step.test.ts:20-34`, extended by Task 1 to yield a different stream per call so a retry can be scripted. It drives the rule's whole truth table: the wait and the retry under the ceiling, the ceiling sentence at 78%, the seven-day sentence, the unknown-weekly sentence, a second limit after one wait, `billing_error`, the event as the only weekly source, the usage call as the fallback, the event winning over a **disagreeing** call (90 from the event against 10 from the call → the step refuses to retry), a seven-day event with no figure falling through to "unknown", a deadline outranking a limit, and the reset rendered both from the SDK's prose and as ISO.

**The live probe** is the `usage:` test in `engine/test/agent-live.test.ts`, env-gated on `SHOWRUNNER_LIVE`, capped at 0.5 USD, one turn, a plain string prompt on `claude-sonnet-5`. It calls `usageMessage(q)` mid-stream (where the executor asks) and again after the stream ends, and prints every `rate_limit_event` the stream carried as the adapter mapped it. **Printed verbatim on 2026-10-15:**

```
usage probe (mid-stream, 183ms): {"available":true,"fiveHour":{"utilization":9,"resetsAt":"2026-10-15T19:50:00.043757+00:00"},"sevenDay":{"utilization":20,"resetsAt":"2026-10-20T18:00:00.043775+00:00"}}
usage probe (after stream, 0ms): {"available":false}
usage probe (message types): ["system","assistant","rate_limit_event","result","system"]
usage probe (rate_limit_events): [{"status":"allowed","window":"five_hour","resetsAt":"2026-10-15T19:50:00.000Z"}]
```

Three things that settles, and one it leaves open:

1. **The usage call answers a plain-string-prompt query mid-stream** — 183 ms, `available: true`, both windows — so the auto-retry rule has a live weekly figure. The `sdk.d.ts` reading that said the call was streaming-only was wrong about this case.
2. **The same call fails instantly once the stream has ended** (`{"available":false}` in 0 ms: the transport closes with the stream). The production call is inside `sdkQuery`'s `for await` loop, which is the only place it can work, and the doc comment records the measurement so nobody moves it out.
3. **The epoch-seconds reading is confirmed from two unrelated encodings.** The stream's five-hour event mapped to `2026-10-15T19:50:00.000Z`; the usage call's own `five_hour.resets_at` for the same window read `2026-10-15T19:50:00.043757+00:00`. The same instant.
4. **Left open: `weeklySource: "event"` has never been seen live.** The probe's stream carried exactly one `rate_limit_event` — `{status: "allowed", window: "five_hour"}` with **no `utilization` field at all**. The preferred source is, on this evidence, the one that does not fire in practice, and the fallback is what a real limit will most likely use. Whether the SDK emits a seven-day event carrying a figure when that window nears its cap cannot be measured without a real weekly limit. The ordering is harmless either way, because an absent event simply falls through.

The measurement Plan I was written for is the s02e01 run of 2026-10-14, `Production/s02e01/runs/20261014T183337Z-8r5w.jsonl` in the live instance: the revise loop's iteration 1 ran 447 s and 48 tool calls and returned `ok: true, subtype: "success"` with the text `You've hit your session limit · resets 7:50pm (America/New_York)`; iterations 2 and 3 resumed the session, made **0** tool calls and returned the same text in 352 ms and 328 ms; the loop failed five seconds after the limit hit with `exhausted 3 iterations without sentinel REVISIONS_COMPLETE`. That run is the one case Plan I exists to make legible, and it is also the one case nothing in Plan I can replay: its log predates the mapping, so it does not carry the mapped events.

## The next plan

- **The season desk as a tool** is the capability still deferred from spec §0 (`docs/specs/2026-09-25-console-rewrite-design.md:13` and `:21`: the desk drafts the premise, and the ninth gate — the idea — returns with it). Plan D's, E's, F's and H's records each defer it, and this one does too. **The s02e01 season-desk convening of 2026-10-08 is its specimen** — the thing a desk tool would have to reproduce; its record lives in the live instance, not in this repository.
- **A usage limit during a *script* step's child process is not covered.** The rule lives in the agent executor, so a Python step that calls an API of its own fails exactly as it did before Plan I. The engine has no equivalent signal to read there: a script's limit arrives as whatever that script prints on stderr.
- **The SDK's usage call is experimental, and its name says so.** `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET()` is wrapped so its absence or its change cannot fail a query, and the probe above measured it working once, on 2026-10-15, against `@anthropic-ai/claude-agent-sdk` 0.3.283. An SDK upgrade that renames or removes it degrades every five-hour limit to "the weekly utilization is unknown" and stops the auto-retry — silently, and with no test failing, because the wrapper's job is to swallow exactly that.
- **The reset's zone is parsed out of the SDK's prose.** `renderResetTime` matches `resets <time> (<zone>)` in the SDK's own sentence, because the `rate_limit_event` carries epoch seconds and nothing else. A reworded SDK sentence degrades the operator's sentence to an ISO timestamp — correct, just less readable — and nothing fails.
- **A limited step writes two `agent_query` events**, the second carrying `resumed: true`. The README's "one per query" contract is honoured, but What-happened lists two queries for one step and an operator counting queries will count one too many. That second event is also what the console reads as "the sleep is over", so the two-queries-per-step shape is now load-bearing: a future executor that resumed a limited query without writing its own `agent_query` would leave the Board saying WAITING for the whole retry.
- **`agent_result.toolCalls` on a waited step is both attempts' total.** The counter is shared so the `agent_tool_call` indices stay unique within the step. The consequence for spec §6.7's zero-tool-call detector (`docs/specs/2026-09-25-console-rewrite-design.md:180`): a retry that did nothing would still report the refused attempt's tool calls, so an empty retry after a limit is **not** detectable from the count alone. `limit` on `agent_result` is what distinguishes that case.
- **Two shows' worth of concurrency in one checkout bit once.** Task 1's fix round ran the console gate over ten of Task 2's uncommitted files in the shared working tree. Its commit named only its own six paths, so nothing of Task 2's was committed, but the 258-passing figure in that report measures the two tasks' trees together. Later plans running tasks concurrently in one checkout should either serialise the gate or give each task a worktree.

## Not built

- **The season desk** (spec §0; every plan's record since Plan D).
- **A fresh-count rule for the gate's fix agent — not needed, because no engine-written log can reach the case.** Ruling I-23 gave a loop a fresh count after a `step_failed` or `step_reset`; the gate's fix-agent shortcut (`runGateStep` skips an `onReject` agent whose `step_completed` follows the gate's last answer) has the same "since the last event" shape and was checked for the same blind spot. It cannot be reached: a fix agent's id is a **nested** id, `orderSteps` refuses a nested id that collides with a top-level one (`engine/src/pipeline.ts:52`), `downstreamOf` walks only `pipeline.steps` and refuses an unknown id (`engine/src/pipeline.ts:21-25`), and both paths that write `step_reset` build their target set from `pipeline.steps` alone — `resetSteps` (`engine/src/runner.ts:115-116`) and a gate's `rerunOnReject`, whose entries are validated against the top-level ids at load (`engine/src/pipeline.ts:91`, used at `engine/src/runner.ts:542-544`). So nothing the engine writes can direct a `step_reset` or a `step_failed` at a fix agent's own id after its `step_completed`; only a hand-edited log could, which is the caveat `runGateStep` already accepts. Recorded as settled rather than left open.
- **A second wait, ever.** One wait is the whole policy: a limit that trips again after the wait fails the step with `… hit its 5-hour limit again after waiting once …`, even when the weekly figure is still under the ceiling. Nothing counts waits across steps or across runs either, so a pipeline that meets the same five-hour window at ten steps in turn will wait ten times.
- **Any warning before a limit lands.** `rate_limit_info.status` carries `allowed_warning`, and nothing reads it. The engine learns about a limit when the limit happens.
- **The per-model seven-day windows' utilizations.** All four `seven_day*` kinds are recognised as weekly windows for classification, but neither source reads a per-model figure: `toUsage` does not map the usage call's per-model rows, and the stream's event source takes a utilization only from the account-wide `seven_day` window (`isAccountWeeklyWindow`). A plan whose per-model weekly quota is the binding one is therefore invisible to the rule — the engine waits on the account-wide number or on nothing.
- **A page-level render test for the Board's waiting line.** `waitingNote(row)` is pure and asserted directly, the server projection is asserted in `console/test/runs.test.ts`, and the Board's own markup is one conditional `<p>` inline in `Board()` — proving it would mean extracting a component to make the `<p>` assertable. The rail's line **is** render-tested (`console/test/client/ProgressBar.test.tsx`), because the rail was already a component that file renders.
- **An exact clock face for `resetLabel`.** It renders in the browser's own zone by design, so the test asserts the shape (`/^\d{1,2}:\d{2}…/`) rather than a literal, and what is pinned is that a parseable ISO becomes a clock time while an unparseable one becomes nothing — which is what keeps `Invalid Date` out of a tab title.
- **Anything on the operator's screen.** No `npm run build` was run in `console/` on this branch, by the plan's own constraint, so the Board, the Run view, the rail and the tab keep their pre-Plan-I behaviour until the controller rebuilds and restarts the server on port 4410. Task 2's work and the fix wave's two console judgments — the wait cleared at the retry's `agent_query`, and no amber for a sleeping run — are unverified against a real browser.
